# Процесс внесения изменений

## Стратегия ветвления

```
main ─────●───────────●───────────●──────────►  только стабильные версии
           \         /           /
            ● ── ● ─●           /                feature/имя-задачи
                     \         /
                      ● ── ● ─●                  feature/другая-задача
```

- `main` — всегда рабочее состояние. Прямой push запрещён.
- `feature/<краткое-имя>` — новая функциональность.
- `fix/<краткое-имя>` — исправление ошибки.
- `docs/<краткое-имя>` — изменения только в документации.

Ветка живёт ровно одну задачу и удаляется после мержа.

## Порядок работы

```bash
git checkout main
git pull origin main
git checkout -b feature/моя-задача
# ... работа ...
./tests/run-tests.sh          # ОБЯЗАТЕЛЬНО перед коммитом
git add -p                     # добавлять осознанно, а не git add .
git commit
git push -u origin feature/моя-задача
```

Долго живущую ветку нужно регулярно синхронизировать с `main`:

```bash
git checkout main && git pull origin main
git checkout feature/моя-задача
git merge main
```

Чем реже это делать, тем крупнее и опаснее будет итоговый конфликт.

## Сообщения коммитов

Формат Conventional Commits:

```
<тип>(<область>): <краткое описание в повелительном наклонении>

<тело: ЧТО изменено и, главное, ПОЧЕМУ>
```

Типы: `feat`, `fix`, `docs`, `test`, `refactor`, `chore`, `revert`.

Заголовок — до 72 символов, без точки в конце. Тело объясняет причину:
что именно сделано, видно из диффа, а вот почему — уже нет.

Плохо: `fix: исправил баг`
Хорошо: `fix(backup): reject retention values below 1`

## Требования к Pull Request

Описание PR обязано отвечать на три вопроса:

1. **Что изменено** — перечень изменений.
2. **Зачем** — какая проблема решается.
3. **Как тестировалось** — конкретные команды и их результат.

PR без ответа на третий вопрос не рассматривается.

## Чек-лист ревьюера

- [ ] **Функциональность** — код делает то, что заявлено в описании PR?
- [ ] **Организация** — нет дублирования, имена говорящие, функции короткие?
- [ ] **Документация** — README, CONFIGURATION, INSTALLATION обновлены?
- [ ] **Потенциальные проблемы** — что будет при пустом вводе, отсутствии
      файла, нехватке прав, запуске из cron?
- [ ] **Поддерживаемость** — разберётся ли другой человек через полгода?
- [ ] **Безопасность** — нет ли незакавыченных переменных, лишних прав,
      секретов в коде, `rm` по непроверенному пути?

## Требования к shell-скриптам

- `#!/usr/bin/env bash` и `set -euo pipefail`;
- заголовочный комментарий: назначение, зависимости, коды возврата;
- пути вычисляются от `BASH_SOURCE`, а не от текущего каталога;
- все подстановки закавычены: `"$var"`, а не `$var`;
- `--help` обязателен;
- любая операция удаления имеет режим `--dry-run`;
- параметры, управляющие удалением, проходят валидацию.
