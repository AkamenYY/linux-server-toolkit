# Диагностика и устранение неполадок

Документ построен по принципу «симптом → проверка → решение».
Общее правило: разбор любой ситуации начинается с `./scripts/sysinfo.sh`.

## 1. Переполнение дискового пространства

**Симптом:** `healthcheck.sh` сообщает `раздел / заполнен на 95%`, приложения
падают с `No space left on device`.

**Диагностика:**

```bash
df -h                                     # какой раздел заполнен
du -sh /var/* 2>/dev/null | sort -rh | head -10   # кто занимает место
du -sh /var/log/* | sort -rh | head -10
```

**Частые причины и решения:**

| Причина | Решение |
|---------|---------|
| Разросшиеся журналы systemd | `journalctl --vacuum-size=200M` |
| Старые резервные копии | Проверить `BACKUP_RETENTION_DAYS`, запустить `backup.sh --dry-run` |
| Удалённые, но открытые файлы | `lsof +L1` — найти процесс, перезапустить его |
| Переполненный кэш пакетов | `apt clean` или `dnf clean all` |

Важно: место, занятое удалённым файлом, который держит открытым процесс,
не освобождается до перезапуска процесса. `du` такие файлы не покажет, а
`df` будет показывать занятое место — классический источник путаницы.

## 2. Скрипт работает вручную, но не работает из cron

**Симптом:** запуск из терминала успешен, в `/var/log/toolkit-*.log` ошибки.

**Причина:** cron запускает задачи с минимальным окружением. Нет `PATH`,
нет переменных из `.bashrc`, рабочий каталог — домашний каталог пользователя.

**Диагностика:**

```bash
* * * * * env > /tmp/cron-env.txt      # временно: посмотреть окружение cron
diff <(env) /tmp/cron-env.txt
```

**Решение:** использовать абсолютные пути и вычислять каталог скрипта от
`BASH_SOURCE`, как это сделано во всех скриптах набора:

```bash
SCRIPT_DIR="$(cd "$(dirname "${BASH_SOURCE[0]}")" && pwd)"
```

## 3. `/bin/bash^M: bad interpreter`

**Симптом:** скрипт не запускается сразу после клонирования на Windows-машине.

**Причина:** файл сохранён с переводами строк CRLF.

**Решение:** в репозитории есть `.gitattributes` с `*.sh text eol=lf`.
Если проблема уже возникла:

```bash
sed -i 's/\r$//' scripts/*.sh
```

## 4. `Permission denied` при запуске скрипта

```bash
ls -l scripts/            # проверить бит выполнения
chmod +x scripts/*.sh
```

Если бит выполнения теряется после клонирования — он не был сохранён в
индексе Git:

```bash
git update-index --chmod=+x scripts/имя.sh
```

## 5. Резервная копия не создаётся

**Диагностика по коду возврата:**

| Код | Значение | Что делать |
|-----|----------|------------|
| 1 | Ошибка конфигурации | Проверить `BACKUP_RETENTION_DAYS` и синтаксис `toolkit.conf` |
| 2 | Ошибка создания архива | Проверить права на `BACKUP_DEST` и свободное место |

```bash
BACKUP_DEST=/tmp/test ./scripts/backup.sh --dry-run
bash -n config/toolkit.conf
```

## 6. Резервных копий стало меньше, чем ожидалось

**Симптом:** в `BACKUP_DEST` лежит только последний архив, хотя срок
хранения — 14 дней.

**Диагностика:**

```bash
./scripts/backup.sh --dry-run | grep 'удалил бы'
grep RETENTION config/toolkit.conf
```

Если `--dry-run` показывает в списке на удаление свежие архивы — значение
`BACKUP_RETENTION_DAYS` некорректно. Скрипт обязан отвергать значения
меньше 1; если этого не происходит — проверять валидацию в `backup.sh`.

## 7. `healthcheck.sh` завершается с кодом 3

Это не ошибка, а штатный способ сообщить мониторингу об отклонениях.
Ошибка выполнения самого скрипта — это код 1.

```bash
./scripts/healthcheck.sh      # посмотреть, какие именно проверки не прошли
```

## Куда смотреть в первую очередь

```bash
./scripts/sysinfo.sh                       # общая картина
./scripts/healthcheck.sh                   # пороговые проверки
tail -50 /var/log/toolkit-*.log            # журналы самого набора
journalctl -p err -n 50 --no-pager         # системные ошибки
```
