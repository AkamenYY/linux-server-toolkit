# linux-server-toolkit

Набор скриптов и документации для администрирования Linux-серверов:
диагностика, резервное копирование и контроль состояния — без внешних
зависимостей, на чистом Bash.

---

## Назначение проекта

На сервере под управлением Linux три задачи повторяются постоянно:
понять, что сейчас происходит с машиной; не потерять данные; заметить
проблему раньше, чем её заметят пользователи.

Обычно каждая из них решается набором разрозненных команд, которые
администратор держит в голове или в личном файле заметок. Это порождает
три проблемы:

- **невоспроизводимость** — два инженера диагностируют одну и ту же
  проблему по-разному и приходят к разным выводам;
- **потеря знаний** — при уходе человека уходит и его файл заметок;
- **ошибки под нагрузкой** — команду `find ... -delete` легко ввести
  неправильно в три часа ночи во время аварии.

Проект решает их, превращая набор устных практик в проверяемый,
документированный и покрытый тестами код.

### Принципы

| Принцип | Следствие |
|---------|-----------|
| Никаких внешних зависимостей | Работает на голом сервере сразу после установки ОС |
| Любое удаление имеет `--dry-run` | Разрушительное действие можно проверить до выполнения |
| Параметры удаления валидируются | Опечатка в конфигурации не приводит к потере данных |
| Осмысленные коды возврата | Мониторинг отличает «сломался скрипт» от «нашёл проблему» |
| Мягкая деградация | Отсутствие утилиты — предупреждение, а не аварийное завершение |

### Доступные скрипты

| Скрипт | Назначение | Периодичность | Коды возврата |
|--------|------------|---------------|---------------|
| `scripts/sysinfo.sh` | Диагностическая сводка о состоянии сервера | по требованию | 0 / 1 |
| `scripts/backup.sh` | Резервное копирование с ротацией по сроку хранения | ежедневно, 03:30 | 0 / 1 / 2 |
| `scripts/healthcheck.sh` | Контроль дисков, памяти и служб по порогам | каждые 15 минут | 0 / 1 / 3 |

У каждого скрипта есть `--help`.

## Процесс разработки

Разработка построена вокруг правила: **`main` всегда работоспособен**.
Любой коммит в `main` можно развернуть на сервер без дополнительных проверок.

Цикл одной задачи:

```
1. Задача            →  ветка от актуального main
2. Реализация        →  осмысленные коммиты по ходу работы
3. Тесты             →  ./tests/run-tests.sh локально, до PR
4. Pull Request      →  что изменено / зачем / как тестировалось
5. Code review       →  по чек-листу из шести пунктов
6. Доработка         →  новые коммиты в ту же ветку
7. Approve и merge   →  merge-коммит, ветка удаляется
8. Синхронизация     →  git checkout main && git pull
```

Прямой push в `main` не используется: любое изменение проходит через PR,
даже правка документации. Это даёт единое место, где зафиксировано, зачем
изменение было сделано.

### Стратегия ветвления

```
main ────●─────────●─────────────●──────────●────►   только стабильные версии
          \       /             /          /
           ●──●──●             /          /          feature/system-info
                  \           /          /
                   ●────●────●          /            feature/backup
                         \             /
                          ●─────●─────●              feature/healthcheck
```

| Ветка | Назначение | Время жизни |
|-------|------------|-------------|
| `main` | Стабильные версии, готовые к развёртыванию | постоянно |
| `feature/<имя>` | Новая функциональность | одна задача |
| `fix/<имя>` | Исправление ошибки | одна задача |
| `docs/<имя>` | Изменения только в документации | одна задача |

Ветка живёт ровно одну задачу и удаляется после мержа. Долго живущие
ветки регулярно синхронизируются с `main` — чем реже это делать, тем
крупнее будет итоговый конфликт.

### Разрешение конфликтов

Конфликт решается **в своей ветке** (`git merge main` внутри feature-ветки),
а не в `main`: это оставляет `main` стабильным на всё время разбора.

Порядок действий:

```bash
git merge-base main feature/моя-ветка     # найти точку расхождения
git log <base>..main                       # что изменилось в main
git log <base>..feature/моя-ветка          # что изменилось у меня
git diff --name-only --diff-filter=U       # конфликтующие файлы
# ... разрешить ...
git add <файл> && git commit               # объяснить решение в сообщении
```

Реальный пример разрешённого конфликта — в истории проекта, коммит
`merge: integrate main into feature/healthcheck`.

## Процесс внесения изменений

Кратко — ниже, подробно — в [docs/CONTRIBUTING.md](docs/CONTRIBUTING.md).

**Сообщения коммитов** — Conventional Commits:

```
<тип>(<область>): <краткое описание>

<тело: что изменено и ПОЧЕМУ>
```

Типы: `feat`, `fix`, `docs`, `test`, `refactor`, `chore`, `revert`.
Что сделано — видно из диффа; почему — только из тела сообщения.

**Описание Pull Request** обязано отвечать на три вопроса: что изменено,
зачем, как тестировалось. PR без третьего пункта не рассматривается.

**Чек-лист ревьюера:**

1. Функциональность — делает ли код заявленное?
2. Организация — нет дублирования, имена говорящие?
3. Документация — README и docs обновлены?
4. Потенциальные проблемы — пустой ввод, нет прав, запуск из cron?
5. Поддерживаемость — разберётся ли другой человек через полгода?
6. Безопасность — кавычки, права, секреты, `rm` по непроверенному пути?

## Процесс тестирования

```bash
./tests/run-tests.sh
```

Каркас написан на чистом Bash и не требует `bats` или `shunit2`: тесты
должны запускаться на любом сервере сразу, включая тот, где что-то уже
сломалось.

Что проверяется:

| Группа | Проверка |
|--------|----------|
| Синтаксис | `bash -n` для каждого скрипта |
| Права | наличие бита выполнения |
| Shebang | первая строка начинается с `#!` |
| Работоспособность | `sysinfo.sh` завершается с кодом 0 |
| Защита от потери данных | `backup.sh` отвергает `BACKUP_RETENTION_DAYS=0` и нечисловые значения, принимает корректные |

Последняя группа — не формальность. Именно эта проверка отделяет опечатку
в конфигурации от потери всех резервных копий, и именно она поймала
реальную регрессию в истории проекта.

Тесты обязательны **до** создания PR. Побочная польза: `run-tests.sh`
пригоден как критерий для `git bisect run` — автоматический поиск коммита,
сломавшего проект.

## Процесс диагностики неполадок

Полный справочник — [docs/TROUBLESHOOTING.md](docs/TROUBLESHOOTING.md).
Он построен по схеме «симптом → диагностика → решение».

Общий порядок:

```bash
./scripts/sysinfo.sh                # 1. общая картина системы
./scripts/healthcheck.sh            # 2. пороговые проверки
tail -50 /var/log/toolkit-*.log     # 3. журналы самого набора
journalctl -p err -n 50 --no-pager  # 4. системные ошибки
./tests/run-tests.sh                # 5. цел ли сам инструмент
```

Если проблема появилась после обновления — расследование ведётся по
истории репозитория:

```bash
git log --oneline -- scripts/имя.sh   # история конкретного файла
git log -S 'фрагмент кода'            # когда строка появилась или исчезла
git blame scripts/имя.sh              # кто и когда менял строку
git bisect start
git bisect bad HEAD
git bisect good <заведомо рабочий>
git bisect run ./tests/run-tests.sh   # автоматический поиск виновного
```

Найденный дефектный коммит откатывается через `git revert`, а не
`git reset --hard`: история сохраняется, полезная работа, сделанная
поверх, не теряется, и не требуется `push --force`, ломающий репозитории
остальных участников.
